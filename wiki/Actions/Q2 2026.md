# Q2 2026 Actions

Derived from synthesis of all current wiki sources. Each action is grounded in a specific non-obvious insight — not a general best practice.

---

## Agent Opportunity Evaluation

**Filter by trust gap, not capability.**
The real deployment bottleneck for agent products is organizational trust calibration, not technical feasibility. Before evaluating any agent opportunity, ask: how wide is the trust gap, and how costly is it to close? Narrow, auditable decisions (fraud scoring, compliance) are faster paths to production than open-ended judgment tasks.

- [ ] Build a simple trust gap assessment into opportunity evaluation: Who reviews decisions today? What would need to be true for them to stop reviewing?

**Filter multi-agent by read/write ratio.**
Multi-agent systems are structurally suited to read-heavy tasks; write-heavy coordination overhead is systematically underestimated (most demos use research tasks because write-task failures are invisible in demos).

- [ ] Before committing to any multi-agent architecture, classify the task breakdown by read vs. write proportion. Write-heavy → budget 3× infrastructure time.

## Agent Build Principles

**Design compaction before prompts.**
Context rot (accumulated history degrading agent performance) means every long-horizon agent workflow needs an explicit forgetting/compaction strategy from day one, not as an afterthought.

- [ ] For any agent build with sessions longer than ~10 turns, specify the compaction step before writing agent logic.

**Design fault recovery before agent logic.**
The dominant engineering challenge in production multi-agent systems is stateful error recovery (idempotency, checkpointing) — a distributed systems problem, not an AI problem. Production reliability is the moat, not model quality.

- [ ] When scoping any multi-agent build, define the failure recovery strategy first. What happens when a subagent fails mid-task?

**Specify inter-agent context contracts first.**
Multi-agent failures are almost always information failures at handoffs, not reasoning failures within agents. The context contract (what is passed, what is compressed, what is discarded) determines reliability.

- [ ] In any multi-agent design, write the inter-agent context handoff spec before writing the agent prompts.

## This Wiki

**Every manual correction is a CLAUDE.md bug.**
The LLM Wiki pattern only compounds if the LLM owns the bookkeeping. Every manual correction that doesn't result in a CLAUDE.md update is doing wiki maintenance manually — breaking the compounding mechanism.

- [ ] After any correction to Claude's filing decisions, update CLAUDE.md with the rule that would have prevented it. Start with categorization edge cases (Meta vs. Ideas vs. Projects).

**CLAUDE.md needs a lint cycle, not just growth.**
Configuration drift (rules added ad-hoc without architectural review) causes inconsistent LLM behavior across sessions. CLAUDE.md is a codebase; it needs periodic refactoring, not just appending.

- [ ] After every 5-10 new rules added to CLAUDE.md, run a lint: check for contradictions, redundancies, and ambiguities.

## Wiki Content Gaps

**Feed personal content.**
Self, People, Projects, Actions categories are empty. The wiki's compounding value depends on cross-domain connections — an AI agents wiki connecting to nothing personal has half its potential.

- [ ] Write one Self page (goals, patterns, identity) from conversation with Claude, not from a source document.
- [ ] Ingest one non-AI source to activate cross-category synthesis.

**File answers back into the wiki.**
Valuable query results (comparisons, analyses, strategic connections) disappear into chat history. The wiki should compound from queries as well as ingests.

- [ ] After any query that produces a genuinely useful synthesis, file it as a new Synthesis or Actions page before closing the session.
